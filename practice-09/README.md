## 1. Цель и результат

Цель — изучить маршруты и middleware Express 5, проверку URL и HTTP-методов, разделение серверных модулей, передачу корректных JSON-ответов и ошибок. В ПР9 реализуется **только чтение** (GET, HEAD, OPTIONS). Изменение данных POST/PATCH/DELETE пока возвращает **405** и будет реализовано в ПР10. Это не дефект и не полная замена изменяющего API ПР8.

Создан сервер из учебной заготовки Express: справочник 3 категорий, выборка из 12 задач, получение задачи по id, четыре проверяемых фильтра, корректные статусы 200/400/404/405/500, заголовки `Allow`, CORS, JSON и `Cache-Control: no-store`. Данные хранятся в памяти конкретного экземпляра приложения и при перезапуске возвращаются к начальному набору.

**ID:** регулярное выражение `/^[1-9]\d*$/` проверяет всю строку, затем `Number.isSafeInteger` предотвращает недопустимые числа; `parseInt('4abc')` использовать нельзя. Некорректный `id` возвращает 400 `INVALID_ID`, а корректный, но отсутствующий — 404 `TASK_NOT_FOUND` с `details.id`.

**Query:** параметры читаются из `new URL(req.originalUrl, 'http://localhost').searchParams` и обходятся до преобразования в объект; так обнаруживаются повторения `q=a&q=b`. Разрешены только `q`, `completed`, `priority`, `categoryId`. Строка `'false'` явно переводится в `false`; `Boolean('false')` запрещён. `categoryId=01` отклоняется, а корректный `categoryId=999` даёт пустой успешный ответ.

**Фильтры:** `selectTasks` не мутирует исходный массив и объединяет условия через «И», сохраняя порядок; регистронезависимый поиск в русскоязычных названиях выполняется через `toLocaleLowerCase('ru-RU')`. `meta.total` — длина **текущей выборки**, а не всего набора.

**Маршрутизация:** GET-маршруты зарегистрированы до обработчиков `router.all`, возвращающих 405, `Allow: GET, HEAD, OPTIONS`. Express обрабатывает HEAD тем же GET-маршрутом, но не отправляет тело. OPTIONS перехватывается middleware приложения до Router. Неизвестный URL получает 404 `ROUTE_NOT_FOUND`, а неожиданное исключение обрабатывается как 500 без утечки стека или внутреннего сообщения.

### 3.1. Листинги

**Проверка id (файл `src/validation.js`):**

```js
export function parsePositiveId(raw) {
  if (typeof raw !== 'string' || !/^[1-9]\d*$/.test(raw)) return null;
  const value = Number(raw);
  return Number.isSafeInteger(value) && value > 0 ? value : null;
}
```

**Фильтрация (файл `src/task-service.js`):**

```js
export function selectTasks(tasks, filters) {
  const query = filters.q.toLocaleLowerCase('ru-RU');
  return tasks.filter(task =>
    (filters.completed === null || task.completed === filters.completed) &&
    (filters.priority === null || task.priority === filters.priority) &&
    (filters.categoryId === null || task.categoryId === filters.categoryId) &&
    (!query || task.title.toLocaleLowerCase('ru-RU').includes(query))
  );
}
```

**Маршрут списка (файл `src/routes.js`):**

```js
router.get('/tasks', (req, res) => {
  const searchParams = new URL(req.originalUrl, 'http://localhost').searchParams;
  const filters = parseFilters(searchParams);
  const data = store.listTasks(filters);
  return res.status(200).json({ data, meta: { total: data.length, filters } });
});
```

## 6. Ответы на контрольные вопросы

1. **Node.js и браузер:** Node.js исполняет JavaScript на сервере и даёт доступ к HTTP/файлам/процессам; браузер содержит DOM и `window`.
2. **Выбор маршрута:** HTTP-метод и путь; query используется уже внутри обработчика и не создаёт новый маршрут.
3. **params и query:** `req.params` извлекает значения из шаблона пути (`:id`), query — из строки после `?`.
4. **`'false'`:** Это непустая строка, её Boolean равен true; преобразовать нужно явным сравнением.
5. **Проверка id:** Проверяется *вся* каноническая запись и безопасный диапазон, исключая `4abc`, нули, дроби и ведущие нули.
6. **Пустой список и 404:** Нулевой результат фильтра — допустимая выборка 200; отсутствующая конкретная запись не найдена (404).
7. **TASK_NOT_FOUND и ROUTE_NOT_FOUND:** Первый означает известный маршрут, но отсутствующую задачу; второй — неизвестный путь API.
8. **405 и Allow:** Путь существует, но метод не поддержан; `Allow` перечисляет разрешённые методы. 404 означает неизвестный ресурс.
9. **meta.total:** Размер ответа после всех применённых фильтров.
10. **Порядок middleware:** Более ранний обработчик может завершить запрос или передать его дальше; 404 нельзя ставить перед Router.
11. **Четыре аргумента error handler:** Сигнатура `(error, req, res, next)` позволяет Express отличить обработчик ошибок от обычного middleware.
12. **Фабрика createApp:** Создаёт независимый экземпляр без запуска порта, удобный для изолированных HTTP-тестов.
13. **Внутренняя ошибка:** Клиенту — фиксированные 500, INTERNAL_ERROR и безопасное сообщение; без стека, секретов и внутреннего текста.
14. **CORS:** Управляет доступом JS браузера к ответу с другого origin, но не аутентифицирует пользователя.
15. **Что добавит ПР10:** POST/PATCH/DELETE, валидацию записей и соответствующих ошибок, управление состоянием и восстановление набора.

## Дополнение для контрольной работы №3 (не изменяет контракт ПР9)

В КР3 четвёртое задание требует `POST /api/tasks` и ошибку `400` при пустом `title`, хотя самостоятельная ПР9 требует **запретить POST с 405**. Поэтому сделан отдельный режим `npm run kr3` (файл `src/kr3-server.js`), который активирует POST-валидацию в существующем Express-приложении. Обычный `npm start` по-прежнему соответствует ПР9. Не запускайте оба режима одновременно: порт один и тот же.

Проверка в новом терминале PowerShell:

```powershell
npm run kr3
```

```powershell
curl.exe -i -X POST "http://127.0.0.1:5505/api/tasks" -H "Content-Type: application/json" --data-binary "@kr3-invalid.json"
```

Ожидается `400 Bad Request`, JSON с `error.code: VALIDATION_ERROR` и непустым `error.details.title`. Для положительной проверки допустимый POST вернёт `201 Created`. Дополнительно `npm run check:kr3` проверяет сохранение read-only режима и новую валидацию. В отчёте КР3 использовать реальные скриншоты именно этого режима, не подменять ответ 405 результатом 400.
