## Реализация программных модулей

###  `src/api-client.js` — HTTP-клиент

Реализованы `ApiError`, `buildUrl` и `createApiClient`. Функция `buildUrl` проверяет абсолютный `http(s)`-адрес, корректно соединяет путь с базовым URL и кодирует query-параметры посредством `URLSearchParams`. Значения `false` и `0` сохраняются, а `undefined`, `null` и пустая строка не добавляются в URL. Входные объекты не изменяются.

Метод `requestJson(path, options)`:

1. Нормализует метод HTTP и разрешает только `GET`, `POST`, `PATCH`, `DELETE`.
2. Отклоняет `GET` с телом до выполнения запроса.
3. Добавляет `Accept: application/json`, а при наличии JSON-тела — `Content-Type: application/json` и результат `JSON.stringify`.
4. Передаёт в `fetch` сигнал, объединяющий внешний `AbortSignal` с тайм-аутом, если внешний сигнал указан.
5. Отдельно ловит сбои `fetch` и различает сетевую ошибку, тайм-аут и явную отмену.
6. Проверяет, что получен `Response`; при ошибочном HTTP-статусе формирует `ApiError` со статусом, машинным кодом и деталями.
7. Для успешного `204 No Content` возвращает `null` без чтения тела.
8. Для остальных успешных ответов проверяет `Content-Type: application/json` и корректность JSON.

**Почему HTTP-ошибка обрабатывается до проверки JSON:** обычный ответ `404` не отклоняет `fetch`, но содержит важный статус; неправильный `Content-Type` у ошибочного ответа не должен превращать `http` в `invalid-response`.

### Таблица ошибок HTTP-клиента

| Вид (`kind`) | Причина | Реакция |
| :--- | :--- | :--- |
| `http` | Сервер ответил `400`, `404`, `503` или другим неуспешным статусом | Сохраняются `status`, `code`, `details`, `url`. |
| `network` | Не удалось получить HTTP-ответ | Показать сообщение о недоступности API. |
| `invalid-response` | Некорректный тип ответа, JSON или схема | Сообщить о неожиданном формате. |
| `timeout` | Истекло время ожидания | Предложить повторить загрузку. |
| `aborted` | Запрос отменён внешним сигналом | Не считать обычную отмену при смене фильтра пользовательской ошибкой. |

### `src/task-api.js` — предметные операции

Создан `createTaskApi(client)`, изолирующий маршруты HTTP от интерфейса:

| Функция | HTTP-маршрут | Результат |
| :--- | :--- | :--- |
| `getTasks(filters)` | `GET /tasks` | `{ tasks, meta }` после проверки коллекции. |
| `getTaskById(id)` | `GET /tasks/:id` | Объект задачи. |
| `getCategories()` | `GET /categories` | Массив категорий. |
| `loadInitialData(filters)` | `GET /tasks`, `GET /categories` | Общий результат двух параллельных запросов. |
| `createTask(draft)` | `POST /tasks` | Созданная сервером задача с назначенным ID. |
| `updateTask(id, changes)` | `PATCH /tasks/:id` | Обновлённая задача. |
| `setTaskCompleted(id, value)` | `PATCH /tasks/:id` | Задача с новым статусом. |
| `deleteTask(id)` | `DELETE /tasks/:id` | Строго `null` (HTTP 204). |
| `resetDemoData()` | `POST /debug/reset` | Подтверждение восстановления набора. |

`getTasks` принимает только фильтры `completed`, `priority`, `categoryId`, `q`; применяет их именно сервер. Валидация ответа отдельно проверяет тип каждого поля, идентификаторы, корректность приоритетов, уникальность ID и равенство `meta.total` длине массива. Ошибки схемы превращаются в `ApiError` с `kind: "invalid-response"`.

### `src/form-validation.js` — проверка формы

Функция `validateTaskDraft(draft, categories)` не обращается к DOM, не делает HTTP-запросов и не изменяет входные данные. Она проверяет название после `trim` (от 1 до 100 символов), приоритет (`low`, `medium`, `high`) и существование выбранного `categoryId` среди полученных категорий. Строковый ID категории из HTML `select` преобразуется в число.

Успех возвращает `{ valid: true, value: { title, priority, categoryId }, errors: {} }`, отказ — объект ошибок по соответствующим полям. Проверка запускается **до POST/PATCH**. При ошибке запрос не отправляется.

### `src/task-view.js` — безопасное DOM-представление

`createTaskElement` создаёт `li.task-card` с `data-task-id`, названием, статусом, приоритетом, названием категории и кнопками `toggle`, `edit`, `delete`. Названия, в том числе переданные сервером HTML-подобные строки, выводятся **через `textContent`**, а не через `innerHTML`. `renderTaskList` вызывает `replaceChildren`, исключая накопление дублирующихся карточек.

`src/dom-app.js` отвечает за события формы, фильтров, кнопок, подтверждение удаления, состояния `aria-busy` и отображение ошибок возле полей. Прямых вызовов `fetch` в нём нет.

### `src/app-controller.js` — асинхронные состояния

Контроллер создаётся через `createAppController({ api, view })` и не зависит от глобального `document`. Он хранит текущий список, категории, фильтры, `editingId`, активный `AbortController` и счётчик актуальности запросов.

| Состояние | Значение | Реакция интерфейса |
| :--- | :--- | :--- |
| `loading` | Ожидание запроса | Сообщение о загрузке и `aria-busy="true"`. |
| `ready` | Получен непустой список | Карточки и число результатов. |
| `empty` | Сервер вернул пустую выборку | Сообщение «По выбранным условиям задач нет». |
| `error` | Запрос завершился сбоем | Понятное сообщение и кнопка «Повторить». |

При первом запуске `start()` использует `loadInitialData` (параллельная загрузка задач и категорий). После получения категорий повторная загрузка использует `getTasks`. Если первая попытка завершилась ошибкой до получения категорий, `refresh()` снова вызывает `loadInitialData`.

**Изменение данных** происходит только после ответа API. Контроллер на время POST/PATCH/DELETE блокирует кнопки через `setMutationPending(true)`, вызывает предметный метод, после успешного выполнения повторно загружает список с текущими фильтрами и снимает блокировку в `finally`. При ошибке входные данные не подменяются предположениями о результате сервера.

**Защита от гонки запросов:** при начале новой загрузки предыдущий `AbortController` отменяется, а каждой загрузке назначается порядковый номер. Результат применяется к интерфейсу только в случае совпадения номера с последней загрузкой. Даже если предыдущий запрос уже завершился или не поддержал отмену, устаревший результат не заменит новый.

**Сервер — источник истины.** `localStorage` не используется для хранения списка; состояние API сохраняется между обновлениями страницы, пока работает сервер, и сбрасывается после перезапуска API.

## Индивидуальный вариант №5

**Тема сценария:** перенос задачи между категориями.  
**Начальный фильтр:** `{ categoryId: 1 }` — категория «Учёба».  
**Адрес:** `http://127.0.0.1:5506/?dataset=variant`.

В `src/variant.js` установлено `variantNumber = 5`; функция `getVariantFilters(5)` возвращает `{ categoryId: 1 }`.

**Проверенный через реальный API сценарий:**

| Этап | Действие | Ожидаемые ID | Фактически в проверке Node.js |
| :--- | :--- | :--- | :--- |
| 0 | Исходный запрос `GET /api/tasks?categoryId=1` | `[1, 7, 13]` | `[1, 7, 13]` |
| 1 | Изменить у задачи `id = 7` категорию с `1` на `2` (`PATCH /api/tasks/7`) | `categoryId: 2` | `categoryId: 2` |
| 2 | Повторить запрос с фильтром `categoryId=1` | `[1, 13]` | `[1, 13]` |
| 3 | Сбросить учебный набор (`POST /api/debug/reset`) | `[1, 7, 13]` | Сброс выполнен; исходный набор восстановлен |

**Объяснение:** когда у задачи меняется категория, сервер сохраняет новое значение. Повторный `GET` использует текущий фильтр, поэтому перемещённая задача больше не входит в выборку категории «Учёба». Изменение массива только в браузере было бы неправильным — фильтр вычисляет сервер.

## Дополнительное задание — длительность последнего запроса

Из списка дополнительных заданий выбран вариант **«вывести длительность последнего запроса через `performance.now()` без изменения предметного API»**.

В `app-controller.js` перед началом загрузки фиксируется время `performance.now()`, а в `finally` вычисляется прошедший интервал и вызывается необязательный метод `view.setLoadDuration(milliseconds)`. В `dom-app.js` добавлен информационный элемент `#load-duration` с `role="status"` и `aria-live="polite"`. Значение выводится как «Последний запрос: N мс».

Дополнительное измерение не меняет HTTP-запрос, структуру предметных объектов, состояние задач и не препятствует штатным тестовым двойникам `view`, у которых метода `setLoadDuration` может не быть.

**Собственная автоматическая проверка №5:** при первой загрузке и `refresh()` контроллер дважды передаёт в представление неотрицательную целочисленную длительность. Фактический результат: **успешно**.

## Отладка и особенности решения

При отладке через DevTools рекомендуется открыть **Network**, включить **Preserve log** и отследить запросы:

- `GET /api/tasks?categoryId=1` — первоначальный фильтр варианта 5;
- `PATCH /api/tasks/7` — изменение категории;
- повторный `GET /api/tasks?categoryId=1` — новая выборка;
- `OPTIONS` перед изменяющим запросом — проверка CORS браузером, если необходима;
- `POST /api/debug/reset` — восстановление исходных данных.

При проверке асинхронного поведения можно включить throttling в DevTools. В контроллере посмотреть `sequence`, `currentController.signal.aborted` и убедиться, что завершившийся старый запрос не вызывает `setTasks`. Секретов и реальных персональных данных проект не хранит.

В рамках практической работы №6 создан клиент браузерного приложения, который выполняет чтение и изменение задач через готовый учебный HTTP API. Реализованы JSON-запросы и обработка кодов `201` и `204`, проверка контрактов данных, типизированные ошибки, клиентская валидация, асинхронные состояния интерфейса и защита от устаревших ответов. Сервер остаётся единственным источником данных. Выполнены и автоматически проверены индивидуальный вариант №5 и расширение с измерением длительности запросов.

**Фактически подтверждено:** 70/70 штатных проверок Node.js и 5/5 собственных. **Браузерный итог 14/14 необходимо подтвердить на компьютере**, поскольку в среде сборки Chromium запрещено открывать локальный адрес.
