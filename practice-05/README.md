## Задание 2. Порядок асинхронного выполнения

Изучен исходный пример `examples/event-loop.js`. В него добавлена собственная микрозадача с меткой `G` через `Promise.resolve().then(...)`.

**Прогноз до запуска:** исходная программа — `A → B → C → D → E → F`. После добавления `G` — `A → B → C → D → E → G → F`.

**Фактический результат `npm run example:order`:**

```text
A: синхронный код
B: начало async-функции
C: конец синхронного кода
D: обработчик Promise
E: продолжение после await
G: дополнительная микрозадача
F: задача таймера
```

**Объяснение:** `A`, `B` и `C` выполняются синхронно. Вызов `async`-функции запускает её тело сразу до первого `await`, поэтому `B` появляется до `C`. Продолжение `await` становится микрозадачей. Сначала выполняются зарегистрированный обработчик `D`, продолжение `E`, дополнительная микрозадача `G`, а потом задача таймера `F`. `setTimeout(..., 0)` не выполняется раньше микрозадач. Если убрать обработчик `D`, останется порядок `A → B → C → E → G → F`.

Полный вывод: [`reports/event-loop.txt`](reports/event-loop.txt).

## Задание 4. Формирование URL

В `src/api-client.js` реализована экспортируемая функция `buildUrl(baseUrl, path, query = {})`:

1. Проверяет абсолютный `http`/`https`-адрес без query и hash.
2. Проверяет непустой относительный путь.
3. Объединяет части без двойного слеша на границе.
4. Кодирует значения стандартным `URLSearchParams`.
5. Пропускает только `undefined`, `null` и пустую строку.
6. Сохраняет `false` и `0`, не меняя переданный объект.

**Примеры проверок:**

| Входные данные | Результат |
| :--- | :--- |
| `"http://127.0.0.1:5505/api/"`, `"/tasks"` | `http://127.0.0.1:5505/api/tasks` |
| `{ completed: false, categoryId: 0 }` | Параметры `completed=false&categoryId=0` присутствуют |
| `{ q: "API & ошибки" }` | Строка закодирована корректно, после разбора URL восстанавливается `API & ошибки` |
| `{ empty: "", none: null, skip: undefined }` | Все три параметра отсутствуют |
| Относительный URL, `ftp://`, query в `baseUrl` | `TypeError` |

При передаче `Object.freeze(query)` входной объект не изменяется. Сценарии 01–04 набора клиента прошли.

## Задание 5. Общий JSON-клиент

В `src/api-client.js` реализованы класс `ApiError` и фабрика `createApiClient` с методом `requestJson(path, options)`.

**Реализованный алгоритм:**

1. Проверка конфигурации `baseUrl`, `fetchFn`, `timeoutMs` и параметров запроса.
2. Формирование URL через `buildUrl` и передача `GET`, `Accept: application/json`.
3. Создание сигнала через `AbortSignal.timeout`; при внешнем сигнале объединение через `AbortSignal.any`.
4. Отдельный `try/catch` именно для этапа `fetch`, чтобы HTTP-ошибка не превращалась в сетевую.
5. Проверка, что получен объект `Response`.
6. Сначала проверка `response.ok`, затем чтение тела. Для ошибочного HTTP-ответа сохраняются `status`, `code`, `details`, `url`.
7. Для успешного `204 No Content` возвращается `null`.
8. Для остальных успешных ответов проверяется `Content-Type`, затем ожидается `response.json()`.
9. Сетевые отказы, тайм-ауты, отмена и ошибки формата преобразуются в `ApiError` соответствующего вида.

**Результаты классификации ошибок:**

| Сценарий | `kind` | Статус / код | Фактическое поведение |
| :--- | :--- | :--- | :--- |

| GET `/tasks?completed=yes` | `http` | `400`, `INVALID_QUERY` | Ошибка некорректного фильтра |
| GET `/debug/error` | `http` | `503`, `SERVICE_UNAVAILABLE` | Ошибка не перепутана с `network` |

| Остановленный API | `network` | Статуса HTTP нет | Сетевая ошибка без `Response` |
| Задержка 150 мс, лимит 20 мс | `timeout` | — | Время ожидания превышено |
| Внешний `controller.abort()` | `aborted` | — | Явная отмена отличена от тайм-аута |

Модульный набор проверяет также неправильный `Response`, корректное декодирование JSON, значение 204 и сохранение исходного `cause`.

## Задание 7. Параллельная начальная загрузка

В `loadInitialData(filters)` запросы `getTasks(filters)` и `getCategories()` запускаются **до** `await Promise.all(...)`. При успехе возвращается `{ tasks, categories, meta }`. При ошибке любой операции Promise отклоняется, что соответствует обязательному контракту.

**Сравнение двух вызовов `/debug/delay?ms=150`** в реальной среде выполнения (три измерения, миллисекунды):

| Метод | Запуск 1 | Запуск 2 | Запуск 3 | Среднее |
| :--- | ---: | ---: | ---: | ---: |
| Два последовательных `await` | 336.8 | 303.7 | 304.4 | 315.0 |
| `Promise.all` | 152.9 | 152.7 | 152.2 | 152.6 |

По результатам испытания два независимых запроса при параллельном ожидании заняли примерно время одного запроса, а последовательное ожидание — суммарное время двух. Разница зависит от условий среды и нагрузки; `Promise.all` не отменяет вторую операцию автоматически при отказе первой.

Источник данных: [`reports/parallel-timing.txt`](reports/parallel-timing.txt); повторение опыта: `npm run example:compare` при запущенном сервере.

## Задание 8. Тайм-аут и внешняя отмена

Проведены два независимых сценария с настоящим API:

## Дополнительное задание А. Частичный результат через `Promise.allSettled`

Создан отдельный модуль `src/partial-load.js` с функцией `loadPartialData(api, filters = {})`. В отличие от обязательного `loadInitialData` на `Promise.all`, функция **не теряет успешно полученную часть**, когда один из запросов завершился ошибкой.

**Контракт результата:**

```js
{
  ok: true,            // оба запроса успешны
  partial: false,       // успешен только один, если true
  tasks: [],            // массив либо null при ошибке задач
  categories: [],       // массив либо null при ошибке категорий
  meta: {},             // объект meta либо null при ошибке задач
  errors: {
    tasks: null,        // либо { kind, message, status, code, details, url }
    categories: null,   // либо такой же объект ошибки
  },
}
```

Каждая ошибка сохраняется структурированно, включая `kind`, а для HTTP-ошибок `status` и `code`. Значение `null` обозначает отсутствие соответствующего результата. При ошибках обоих запросов `partial` равно `false`, поскольку успешной части нет.

**Четыре проверенных сценария:**

| Сценарий | `ok` | `partial` | Задачи | Категории | Ошибки |
| :--- | :---: | :---: | :--- | :--- | :--- |
| Оба запроса успешны | `true` | `false` | Сохранены | Сохранены | Обе `null` |
| Задачи недоступны, категории получены | `false` | `true` | `null` | Сохранены | `errors.tasks`: `http`, 503 |
| Задачи получены, категории недоступны | `false` | `true` | Сохранены | `null` | `errors.categories`: `network` |
| Оба запроса отклонены | `false` | `false` | `null` | `null` | Обе ошибки записаны |

Для повторения: `npm run example:partial` и `npm run check:own`. Все 4 сценария пройдены. Исходная функция `loadInitialData` **не заменялась** и продолжает использовать `Promise.all`, как требует обязательная часть.

## Вывод по работе

В ходе практической работы реализован переиспользуемый HTTP-клиент с `fetch`, `async/await`, проверкой успешности ответа и формата JSON. Предметный модуль получает задачи и категории с сервера, валидирует схему и выполняет независимые запросы через `Promise.all`. Для ошибок используются структурированные объекты `ApiError` с раздельными категориями `http`, `network`, `invalid-response`, `timeout` и `aborted`.

Проверены синхронный порядок выполнения, микрозадачи Promise, таймеры, URL-параметры, внешняя отмена, ограничение времени и обработка сетевого отказа. Индивидуальный вариант №5 вернул три ожидаемые задачи `[1,7,13]`. Дополнительное задание А реализовано через отдельную функцию с `Promise.allSettled`, сохраняющую частично успешные данные. Исходный сервер остался неизменным. **Все 57 тестов преподавателя и 7 собственных тестов пройдены без ошибок.**
